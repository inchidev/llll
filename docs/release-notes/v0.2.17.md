# L4 0.2.17

This release completes recovery for a Cloudflare Factory that was provisioned with an earlier image but never activated. Landing, Shell, installer, Server, portable runtime and Docs share **0.2.17**. Existing customer Servers stay pinned until their operator chooses an update.

- After updating the Server, provisioning can replace its unused Factory image and limits only when its database has no Cloudflare Factory Node and no retained Task source. Existing Nodes, including paused ones, and retained source keep their pinned provider. A provisioning marker serializes this repair against activation and remains closed after a failure until provisioning succeeds. The installer requires the immutable Server artifact to advertise this protection.
- The existing Container application is reconciled through a Cloudflare rollout, then checked for the selected image, size and namespace before activation is allowed. A foreign namespace or different scheduling policy requires inspection. No Task source, Server data or backup destination is deleted.
- Settings → Repositories offers **Review Factory provisioning** when Factory resources exist but activation has not created a Node.
- The release picker bypasses old browser cache entries. Cloudflare's official zone now respects the application's cache headers, so the release list uses its intended five-minute cache. A completed update no longer asks you to keep waiting for verification.

The single-compressed image layers and semantic publication checks from 0.2.16 remain in place. Published 0.2.15 and 0.2.16 assets are unchanged.

For failed 0.2.15 Factory activation: update the Server to **0.2.17** with a verified backup, open **Review Factory provisioning**, confirm the desired resources, provision again and activate Factory. A Server with an existing Factory Node or Task source must preserve/export that source and explicitly configure another provider; this release does not replace active authority.

No Server SQL or Durable Object migration is required. The existing `server-v1` lineage and `v5-factory-executor` migration are unchanged.
