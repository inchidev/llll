# Governed agents

An Agent is a non-human Member with one assigned Role. Its profile contains its name, instructions and model. Creators with Manage roles can choose or change its Role in the Create/Edit agent dialog. Roles can also be changed in Settings → Roles → Members; Agents appear in that list alongside people. The Owner role cannot be assigned.

## Getting started

1. **Create an Agent.** Server settings → Agents → Create agent. Give it a name no other Member uses, a model (or leave the Server default) and profile instructions. People cannot rename themselves to an Agent's name either.
2. **Choose its Role.** Members with Manage roles pick the Role in the same dialog or in Settings → Roles → Members. The Role caps what the Agent can do; the Owner role is never assignable.
3. **Let people use it.** Grant **Use agents** to the Roles (or Project policies) whose Members may find and invoke the Agent. Without it, the Agent is hidden from their member list, MCP `list_members` and Agent DMs.
4. **Message it.** Open a DM from Agents, or mention it in a conversation it can access. Each reply is a Run governed by both the Agent's and your permissions.
5. **Give it Tasks.** Assign a Task to the Agent, then choose **Run assigned agent**. Task execution needs Read tasks, Execute assigned tasks and Send messages for both the Agent and you.
6. **Follow its work.** **Runs** (from Agents or any Run page) lists the Runs you started, filterable by status and Agent. Each Run page shows its activity timeline, model requests and result.
7. **Pause or delete it.** Pausing stops new work and keeps everything. **Delete agent** in the editor is permanent for new work; see below.

## Deleting an Agent

Delete agent requires Manage agents and authority over the Agent's current Role (the same hierarchy as editing it). Deleting:

- removes the Agent from the directory, Settings, Task assignee lists and MCP `list_members`, and frees its name;
- cancels its queued and running Runs and its active Schedules, and revokes MCP connections and access tokens acting as it;
- unassigns its open Tasks (completed Tasks keep it as their assignee for history) and returns Ready Tasks to Backlog;
- deletes its avatar file.

Messages, Direct Messages, Runs, Task results and audit entries stay. Its DMs become read-only like any DM with a removed Member. The audit log records `agent.delete` with what was stopped. A deleted Agent cannot be restored; create a new one instead.

## Role permissions

- Using agents: `useAgents` discovers Agents and permits invocation in accessible conversations. It does not reveal other members' private Direct Messages.
- Administration: `manageAgents` edits profiles; it does not by itself permit private conversations or tool execution.
- Approval: `approveAgentActions` approves pending actions in accessible conversations. External email still requires approval.
- Tasks: `readTasks` reads; `writeTasks` creates/updates; `manageTasks` additionally administers boards and destructive operations.
- Data: `readData` reads; `writeData` edits records and Documents; `manageDatabases` additionally changes structure and deletes resources.
- Apps: with `manageGadgets` and `manageDatabases`, an Agent drafts Apps (`list_app_drafts`, `get_app_draft`, `create_app_draft`, `update_app_draft`) over Database Views both it and the initiating person may use. It never chooses who may open an App and never publishes: a person with Manage Apps does both in Apps, and the published version stays unchanged until then.
- Autonomy: `executeTasks`, `useComputer`, and `manageSchedules` are separate opt-in permissions, never inferred from an administrator role.

Create/Edit agent shows the selected Server Role. Templates provide starting instructions only; they do not grant access. Assign reusable Project policies in the Project's access settings. The same person or Agent can be a Developer in one Project and a Reviewer in another. Server Role grants remain additive and can be broader than a Project policy.

The Role editor selects all or specific Boards, Tables, Documents and Canvases. Selecting no resources permits none of that kind. Grants govern operations; selecting a resource does not grant an operation. Restricted collections cannot create new top-level resources. Role administrators cannot grant permissions or resources they lack.

Internal agent tools check the Agent's own Role plus the initiating person's delegation. Invoking an Agent as Owner never makes the Agent an Owner. Agent access can widen that delegation for one Agent: in the Agent's editor, **Who can use** lists people and Roles with a Policy, a scope (one Project or the whole Server), an optional daily Run limit and an end date. Only someone who holds those permissions in that scope can give them; removal stops Runs that relied on them. **Answers** chooses whether everyone who uses agents can invoke it or only the Owner and holders of access; a mention from anyone else does not wake it. See [ADR 0004](adr/0004-grants-and-agent-access.md). MCP independently intersects the current acting Member's role/resource access with connection scopes. Tool access is checked at execution, rather than trusted from model instructions.

## Upgrade behavior

Existing server managers retain Agent use, profile administration and conversational approvals. Existing Task/Data managers retain their previous access. No existing role acquires autonomous execution, computers or schedules through migration. Existing resource access stays unchanged until explicitly restricted.

## Runtime implementation

All profiles use Pi. The default embedded executor uses `@earendil-works/pi-durable` 1.4.0; a Task's box and the Docker and Cloudflare container executors use the pinned `@earendil-works/pi-coding-agent` 1.3.0. Runtime names are internal and there is no runtime selector. The former Think engine is retired; old profile metadata is normalized to Pi, and no Think context is imported. Pi needs Server file storage (KV or R2) and a model provider. Provider keys remain at the Server; compute receives a capability for one active Run.

Runs are durable, bounded attempts. Every model/tool call reloads current Agent and initiating Member authority and the saved Project/resource ceiling. Removal, pause or reduced access revokes execution. In Settings → Agents → Execution, the Owner can set limits for new Runs. Defaults are six hours, 256 steps and model calls, 4,096 tool calls and two million tokens; per-Agent defaults are 500 Runs and 20 million tokens in 24 hours. An identical non-control tool call stops after six attempts. Delegated Runs share the root model, token and tool budgets and execution window; depth and child count are bounded. A tool with an uncertain outcome is never silently replayed.

An answer streams into its conversation while Pi writes it. The conversation's Durable Object keeps the current turn in memory only and sends it over the conversation's WebSocket; a client that connects mid-answer receives the text so far. A tool call starts a new turn. Nothing of a stream is written to D1: the finished message replaces it and is written once, and the Run's stored events keep its steps, not the text. Everyone in the conversation watches only while the finished text would be posted there: an autonomous Run without a Task that has not read a private source, or one in a direct conversation with its initiator alone. Otherwise only the initiating Member watches, as only they may open the private Run. Embedded Pi streams as it writes. A Task's box pushes its events to the gateway about every 150 ms while text flows, and the Run streams them the same way. A container executor without a box is polled every 750 ms while it writes. An Agent's answer may be up to 12,000 characters; a person's message stays at 2,000.

Web research requires Browse web for both the Agent and initiating Member. Search uses an Exa key (Server settings → Integrations, or `EXA_API_KEY`) or an explicitly assigned OpenRouter `web.search` model; reading pages additionally needs a configured Browser provider. Task-backed repository work requires Use computer for both parties and a connected Compute Node. The Agent then works on the Task's box with Pi's own read, write, edit and shell tools; anywhere else the runtime refuses them. The box reaches only this Server and its Project's network, plus windows a person opens; see [Software Factory](software-factory.md). A Project coordinator with Delegate project tasks can start another Agent's assigned Task in the same Project, wait for its private result, and create a new numbered attempt after feedback. The original person's authority and shared budgets still apply.

Schedules support one-time, daily and weekly reminders and task execution. They retain their original role/resource ceiling, preserve the chosen wall time across DST, skip missed repetitions, and deduplicate each occurrence. Current membership and grants are checked before delivery. Changing permissions can block an existing schedule; edit it to save the current role as its new ceiling, or create a new mandate after reviewing the new role. Manage your schedules at `/schedules`; see [Schedules](schedules.md) for limits, blocked reasons, recovery and the API.

### Embedded executor (experimental)

The embedded executor runs `@earendil-works/pi-durable` 1.4.0 inside the Run SQLite Durable Object when neither a Runner nor Cloudflare Containers is configured. It needs the Run DO, file storage and a model provider. Its registered L4 tools use the same Server gateway, current role checks, delegation ceiling, call IDs and result ledger as container execution. Tasks, Data, schedules, web search and configured Browser reads are available only when authorized. There is no local shell or filesystem; do not treat it as a container for arbitrary code execution.

A durable input snapshot and stable submission ID let polling reopen active SQLite work after eviction. Recorded tool results can be read again; uncertain external writes are refused. Stop aborts the harness and in-flight inference, as well as revoking further gateway access. Model output and tool activity stream into bounded Run events and conversation progress. Archives are chunked atomically into bounded SQLite rows; automatic context compaction uses the same inference gateway and budget.

Local celld acceptance on 2026-10-23 used a real OpenRouter model, called `list_tasks` and `search_web`, returned a direct documentation URL, and cancelled an active model call without publishing a result. An independent process test kills execution with SIGKILL after a tool’s external write and resumes from SQLite: the user input and write each occur once. Other tests cover archive ordering, steering at a tool boundary, duplicated steering delivery, permission revocation, inference budgets and multi-megabyte Unicode archive storage. These are local and fixture results; Cloudflare Preview acceptance remains a separate release check.

### Model providers and conversation controls

Server settings → Models → Providers stores API keys encrypted with the Server’s `AUTH_SECRET`. Only the Owner can replace credentials, enable a provider, enable OpenRouter web search or choose the Server default. Members with `useAgents` can see available model IDs, never credentials. A blank key preserves the saved key. OpenRouter, Claude and ChatGPT are available through Pi; no alternate agent engine is offered. Legacy bare model IDs retain their deployment endpoint or resolve to one unambiguous enabled connection. Disabled and ambiguous selections fail with an actionable error, never silently falling back to another model. Disabling a saved provider fails closed; importing OpenRouter suppresses the corresponding legacy deployment option. The import action never sends the deployment key to the browser. Existing deployment bindings remain a compatibility fallback until imported.

- OpenRouter: Chat Completions with an API key. Its optional web search plugin is a separately billed, role-gated tool, with at most three sources per search and the Run’s model/token budget.
- Claude: Anthropic API key. Claude Pro/Max subscription authentication is not implemented in embedded Pi. Do not collect Claude.ai credentials or reuse subscription OAuth tokens as shared Server API credentials; see [Claude authentication boundaries](https://code.claude.com/docs/en/legal-and-compliance).

In a one-to-one Agent conversation, the toolbar above the composer selects the provider/model for future Runs, switches Queue/Steer and stops outstanding work. Threads inherit the parent conversation’s model selection. An admitted Run snapshots its model; changing the picker does not switch an in-flight generation. Every root invocation opens a thread in a DM or channel; replies inside that thread keep using it. Queue runs admitted into the same thread share context sequentially. Failed runs post an error with a link to details. Only the initiating Member can retry a stopped Run, under their current permissions. On embedded Pi, Steer adds the initiating member’s new instructions at the next tool boundary of their active Run, using a stable message ID. It cannot inject instructions under another member’s delegation. The interaction follows the [T3 Code composer](https://github.com/pingdotgg/t3code/blob/main/docs/user/composer.md); container adapters currently queue when steering is unavailable. Agent conversations appear in the dedicated Agents app, separately from human Chat.

### Task boxes

A Task Run whose repository environment names a connected Compute Node runs on that Task's box: one long-lived container per Task, on a VPS Node or as a Cloudflare container, with an ordinary Git checkout. Its submission says `computer` and `box`, and the box runtime runs Pi there with its native tools in `/work/repo`. The box calls the model and the Run's L4 tools through the Server's gateway with a capability scoped to the Run; provider keys stay on the Server. It pushes its events and its session through the gateway's `events` and `session` operations. The Run keeps only events after what it already has, streams new ones to the conversation, wakes on the result and answers with cancellation and steering. A Run without a box never gets native tools, including a restored Run with an earlier computer mandate. Setup, isolation and limits are in [Software Factory](software-factory.md).

### VPS executor

For Runs without a box, a VPS Server can run container Pi. Build both images from the checked-out release, then select their immutable digests in `LLLL_AGENT_IMAGE` and `LLLL_AGENT_RUNNER_IMAGE`. Add `self-host/compose.agents.yml` to the Server Compose command, and configure a separate 32+ character `LLLL_RUNNER_TOKEN`, persistent `LLLL_SERVER_ID` and Compose project name `LLLL_PROJECT`. The trusted Runner has Docker control. Agent containers have no Docker socket, public internet route or provider/production credentials; they run as a non-root user with a read-only root, limited CPU/memory/PIDs bounded temporary data (512 MiB), bounded logs and no persistent host file mount. The Server joins their private network solely to provide the authorized gateway. Results/context are archived before compute is removed. Losing an active compute process interrupts the attempt; a new attempt restores archived conversation context and never silently replays uncertain external actions.

### Cloudflare executor

For Runs without a box, a Cloudflare Server can run container Pi. Add the optional `AGENT_COMPUTE` binding for `AgentComputeDurableObject`, a new SQLite class migration, and a Container with `scheduling_policy: "durable_object"` and named `images.pi` pointing at `packages/agent-runtime/Dockerfile` with repository-root build context. The adapter uses the direct Container API, denies public egress and intercepts only the Server gateway. These provider-specific settings stay outside the Pi protocol. Run application builds/deployments only through Workers Builds from Git. The isolated Server Preview supports `LLLL_PREVIEW_PI=1`; it never changes production or customer Servers.

Native Pi `read/write/edit/bash/grep/find/ls` tools are disabled in these container executors. Runtime admission rejects `computer: true` outside a box; the Server submits `computer: false` there while retaining the repository mandate for permitted broker reads.

The Docker proof uses the real Pi SDK with a deterministic model fixture; it proves execution/isolation/recovery, not real-model quality. A Cloudflare Preview and authenticated product acceptance are separate required evidence.

### External agents

An external Agent, such as Grok Bot, works on its own computer and never uses this Server's model providers. In the Agent editor, turn on **Its own computer (external agent)** and enter its webhook URL, the header that carries its sender key, the key and a reply timeout (2–120 minutes, default 20).

1. A direct mention or a DM message admits a Run as usual: the same Role, mandate, conversation queue and daily Run limit apply. Role and group mentions never wake it.
2. The Run's coordinator sends one `POST` with `Idempotency-Key: <Run ID>` and a JSON body (`type: "agent.run"`, `version: 1`): the Run, the Agent, the invoking Member, the conversation, the message text as `prompt`, `reply: { tool: "send_message", arguments: { channelId, replyToId } }` (`replyToId` is the source message, when there is one) and `complete: { tool: "complete_run", arguments: { runId } }`. The prompt is untrusted data. Redirects are not followed, and only public `https://` hosts are accepted. Network errors, 408, 429 and 5xx are retried up to five times; any other status fails the Run with the status shown.
3. The Agent works through this Server's MCP (`/mcp`) with an access token or OAuth connection that acts as the Agent (User Settings → Connections → Tokens or Connected apps), within its Role and the authority of whoever created the token ([ADR 0004](adr/0004-grants-and-agent-access.md)). That credential is not bound to the Run, so the limit on other Runs, no higher than the person who asks, does not hold here. An external Agent is therefore always *granted*: it answers only the Owner and holders of its Agent access, and whoever it answers can reach everything its Role allows, whatever Policy their access names. Keep its Role narrow. It may post any number of progress messages, here or elsewhere. Its `send_message` reply to the source message (`replyToId`) in the Run's conversation is its answer and completes the Run like `complete_run`.
4. Otherwise the Agent calls `complete_run` when it is done. `outcome: "completed"` requires its answer in the Run's conversation and closes the Run with its latest message there; the Server does not post it again. `outcome: "failed"` closes the Run and posts its `note` as the reason. Only the Agent itself can complete its own Run.
5. Without either, the Run settles at the reply timeout: completed with the Agent's latest message if it replied, failed with a note otherwise. A later mention starts a new attempt.

Several external Agents may belong to one outside account, such as the bots of one Grok Bot account. Give each its own Agent, webhook and MCP access token so messages and Runs are attributed exactly; a bot that answers through another bot's connection posts under that Agent's name and cannot complete its own Run, which then fails at the timeout. Such bots usually share connections and files on their side, so treat the account as one trust boundary: what one of them may read, all of them can. Separate their Roles for focus, not for secrecy, and grant a private channel or Mailbox to one only if every bot of that account may see it.

The sender key is encrypted with `AUTH_SECRET`, is never returned to the client, and must be entered again when the URL or header changes. Deleting the Agent deletes its webhook.

## Untrusted context and sensitive tool calls

The Server enforces a conservative containment policy for #289 before expanding capabilities. Tool results, Task prompts, restored transcripts and messages supplied by another Member are untrusted context. A durable flag belongs to the entire Session: retries, failed reads, cached result replay and fresh Runs in that conversation do not clear it. Migration 0019 backfills existing Sessions with prior Task/tool/transcript context. A new conversation has independent context; it does not acquire authority to disclose another conversation’s data.

In the default autonomous mode, classified tools can execute within the current Agent and initiating Member permissions, resource access and saved Run scope. The Server rechecks authority before each effect. Unknown tools are blocked. External source content remains untrusted and does not grant new authority. In review mode, other writes and outbound calls are blocked. For code work the mode gates what leaves the Task's box, not commands: in autonomous mode the Agent pushes its own branch, opens windows to its Project's network and uses the Project's bound secrets on its own; in review mode each push waits for the initiating person, who reads its diff, and a secret is used only through a window they opened; plan mode sits between them, with one plan the Agent proposes through `factory_plan` (summary, steps, hosts and secrets) that the initiating person approves once in the Inbox or the Run and that then covers pushes and the hosts and secrets it names. A host outside the Project's network always waits for a person, unless an approved plan names it. Publication additionally requires Propose code changes. Every outward request is a `factory_approvals` row with a digest over its exact SHA, ref, host or plan, answered once; a tool call that waits is asked again with the same call identity until it is decided. Runs admitted before execution modes existed retain review behavior.

Connection administration and SDK/SSE health checks remain available to authorized humans. Tool discovery and execution apply the same execution mode, current permissions, connection grants and revisions. Enabled MCP connections do not grant access by themselves. Model output and external sources are untrusted; the Server retains private Run content and action receipts.

Run details shows the untrusted-context state and bounded context-policy decisions. These decisions indicate only that the context guard allowed/blocked a call, not that an operation completed. They contain known tool/effect categories and reasons, with no arguments, results, URL contents or credentials. External and unknown tool identities are redacted. Existing execution ledgers still control uncertain outcomes and duplicate writes. General Server audit does not receive private tool payloads. Prompt wording is guidance, not the security boundary; this policy does not claim to solve every form of prompt injection. Run details, events, transcripts and files are private to the initiating human. Queue prompts are redacted for other Members. Governed Run progress never broadcasts model text, including historical stored partials. All model-generated final output is retained privately by default, including a clean first Run; shared chat and Task results receive only a Server-generated notice/link, while the fixed Task Review transition remains governed by its existing mandate. The initiating human can explicitly review and share a completed result as described below; automatic publication remains blocked.

## GitHub code work

Settings → Git configures a source repository and a working repository (the same repository by default, or an optional fork in the same GitHub network). A task selects that environment; Roles select source repositories by their stable GitHub IDs. Both the initiating Member and Agent require `useComputer`, task access and repository access. The Agent additionally requires `proposeCode` to publish changes. Existing administrator roles do not acquire publication permission.

Create a **dedicated GitHub App**, separate from login OAuth, through Settings → Git → GitHub (see setup below). Select its repositories on GitHub, then explicitly select that connection in L4. Existing deployments may instead provide `GITHUB_AGENT_APP_ID` and its PEM `GITHUB_AGENT_APP_PRIVATE_KEY` as deployment secrets; this is a separate compatibility option, not a required first-setup step. Authorize only selected repositories and any optional working forks. Grant repository Contents read/write, Pull requests read/write, Issues read, Checks read, Commit statuses read, Actions read and Deployments read. The broker mints narrower single-repository tokens per operation: source Contents read; working repository Contents write; a box's approved push Contents write, revoked after the push; source Pull requests write; source Checks/statuses read; a merge from L4 (a person from the Task, or the Agent under the Project's `agent_after_checks` Git flow) source Contents and Pull requests write, used once for that merge. Tokens and the App key never enter compute. Repository discovery uses metadata-only credentials and revokes them after use. All GitHub API requests use manual redirects; credentialed requests never follow a redirect. The archive broker accepts only GitHub’s 302/303 redirect to the configured repository’s exact admitted SHA on codeload.github.com, downloads without App credentials, rejects further redirects and rechecks current access before returning cached or downloaded code.

Task-backed code Runs can discover `read_github_repository`, `read_github_issue` and `read_github_pull_request`. These read only the configured source repository: callers select an issue/PR number and a bounded section/page, never a repository URL or HTTP method. Issue comments, PR patches, review summaries and inline comments are paginated at 20 entries for at most 10 pages, with explicit truncation. PR file/review reads recheck the head and base SHA and reject evidence collected across a changing revision. Remote text and patches are untrusted data, not instructions. Issue/PR tokens add only the necessary read permission to the one source repository; App setup must include Issues read. Cached repository archives also require a fresh dedicated-App capability, so a revoked installation cannot reuse private cached code. Current Run, Role, initiator, Task and repository authorization are checked before requests and before returning results. Linking issue/PR metadata in the Task editor and real-installation acceptance remain separate follow-up work.

An admitted Run freezes the environment version, base branch and exact commit/tree. Changing or disabling the environment revokes active Runs and stored schedule mandates. With a Compute Node the Run works on the Task's box, as [Software Factory](software-factory.md) describes, and publishes with `factory_publish`. Without one, the runtime downloads a bounded source archive through the Server gateway, creates a local Git base, edits files and can run available local checks. Public network access stays disabled there: package downloads and network-dependent tests are unavailable. Dependency-heavy projects must rely on their independent CI checks; agent reports are not CI evidence.

Without a box, `publish_code_changes` gathers local changed text files and creates or updates one Run-owned branch (`l4-agent/<run-id>`) in the working repository, then a draft PR to the source's configured base. Proposals cannot change `.github` or `.git`, force-push, change the base branch, merge, label a release or deploy production. Repeated publication recovers the same branch/PR after an uncertain response. A branch changed outside the Run requires a new reviewed attempt. Required CI names are checked against the exact published commit; missing or failed checks keep it unverified. Preview links must use HTTPS on configured domains; their presence does not prove authenticated product acceptance.

Its outputs are bounded to 100 changed files and a 2 MB JSON archive, including binary files and deletions; individual files are at most 500 KB. The Run page downloads the archive through current conversation/task/repository authorization. Future attempts restore files only from the same conversation, task, environment version and base commit. Repository archives are limited to 20 MB compressed / 200 MB expanded and 10,000 ordinary files/directories; links and special files are rejected. A fresh base commit starts with fresh files. Results and transcripts remain in private Server storage after ephemeral compute is removed.

MCP `create_table` requires the explicit `data:manage` connection scope plus the current Role's table administration and resource grants. Existing tokens do not gain this scope. HTTP, internal tools and MCP share the same table/record services and current-role checks.

Production publishing stays with the protected GitHub release process: a human reviews and merges a release PR with the release label and shared version increase. That authority and its credentials are outside the agent runtime and GitHub broker.

## Model connections

The Server owner manages connections in Server settings → Agents → Providers. Agents and Providers have separate searchable, paginated lists. Model defaults appears before the provider list. The owner-only Audit tab separates Run status and usage from agent-related configuration changes and actions; both views support search and pagination, and Run rows omit prompts and transcripts. A row opens Run details with its prompt, events, selected model, individual model requests, safe provider errors, archived transcript download and retry. Access is rechecked against the conversation and any Task/code environment. Multiple connections of the same provider type can have distinct names. API-key connections show only a masked key fragment to the owner. Model catalogs come from the provider; choose models by name instead of entering IDs. The conversation picker combines the connection name and model, and searches a bounded model page on the Server.

ChatGPT / Codex uses **Continue with ChatGPT** with the [official open-source OAuth flow](https://developers.openai.com/siwc/token-sharing-open-source/sign-in). Pi remains the runtime. The owner authorizes ChatGPT plan usage; by default that connection pays only for Runs initiated by that same member. Any member with Use agents can connect their own ChatGPT plan in Settings → Models; Server API keys stay Owner-only. The connecting member can turn on **Share with everyone on this Server**, and then any member's agents and AI functions may use that plan and count against its limits; only that member can change sharing. It does not sign anyone into L4, link local Accounts, or grant membership. Tokens and refresh credentials are encrypted on the Server and never passed to Pi. Model selection and inference use the public OpenAI API and the account's model catalog. Live ChatGPT authentication/inference has not been accepted yet; OAuth, renewal, identity validation and stream termination have fixture coverage.

For a local HTTP Server, the browser returns to `127.0.0.1` on the Server port. A remote Server cannot receive that return, so after approving, the member copies the address of the `127.0.0.1:1455` page ChatGPT opens and pastes it into L4, which completes it with the same one-time state and PKCE check. Submitting the same address again confirms a finished connection or repeats the original failure. Removing a ChatGPT connection stops local use and attempts to revoke the renewable session; if remote revocation fails, disconnect L4 in ChatGPT settings.

In an agent DM, a message starts a reply thread. Direct Run admission into the DM root is rejected. New messages queue in send order across that DM's threads; **Steer** on an already queued message submits it to the sender's running embedded Pi attempt at its next tool boundary. If steering is unavailable, the message stays queued. If delivery is uncertain, it is not executed a second time. **Stop** appears while the agent is working and cancels pending work before the active attempt. Separate conversations can run concurrently within the existing limits.

## Model selection and task completion

Connecting a provider adds choices; it never selects the first model as a Server default. Choose the default explicitly in Providers, or select an Agent/conversation model. A disabled default does not fall back to another model. Explicit operator model configuration remains supported; an AI binding by itself does not enable a default. Workers AI appears as a deployment connection whose account access, quota and compatibility are verified on use. Known OpenRouter models without tool support are excluded from Agent choices; missing capability metadata is not proof of incompatibility.

Task execution requires Read tasks and Execute assigned tasks, plus access and Send messages in the report conversation, for both the Agent and initiator. Admission checks these before inference. Completion can record only that Run’s result on its assigned, unchanged Task; it does not grant general task editing. Results move to Review. Human changes, reassignment and archival are preserved.

Assignment alone does not start execution: Ready means available for an explicit start. Choose **Create and run** when creating an Agent-assigned Task, or **Run assigned agent** at the top of a saved Task. A separate report channel is optional: without one, the Agent posts in the Task’s discussion, which uses the board’s existing access rules. The discussion is created on demand when the caller can write Tasks. Save any pending Task edits before starting; paused Agents and archived Tasks explain their blocked action beside the button. Both actions use the same authorization and admission checks. Conversation reports identify the Task number, title and current status, link back to its board and detail, and include the result below.

Computation, Task-result recording and report delivery have independent states on the Run page. Delivery failures retain the computed result. Pending delivery retries are bounded; only the original initiator can explicitly retry blocked delivery, under current permissions and the saved mandate. Retrying delivery does not call the model. Successful delivery is not posted twice.

Every model request includes the current UTC time and Server timezone (UTC by default). The `get_current_time` tool refreshes this reference during longer work. Ambiguous scheduling timezones still require clarification.

## Tool discovery

Both embedded and container Pi start with `search_tools`, `get_tool_details` and the current-time tool. Other Server tool schemas are deferred. Search ranks only the Run's currently permitted capabilities and returns at most eight short summaries without schemas or resource names. Load an exact identity with `get_tool_details(name, purpose)` to expose its schema on the next model request. The purpose is a short public description of the requested work, not private model reasoning; it appears in Run activity. Details include effects, prerequisite action, output/evidence, cost hints and trust boundaries. Search metadata does not grant permission.

Each Run may select at most eight tools, with at most 16 KB per descriptor and 32 KB total. Discovery and selection use the existing tool-call ledger and budget. Unselected schemas do not enter model requests. Missing matches and unavailable details explain that a capability is missing. Search disappears when its assigned provider is disabled or unavailable, unless Exa is explicitly configured; page reading requires Browser access. Repository tools require the existing repository/computer mandate. Connection changes are checked on the next discovery and invocation; reduced Role/resource authority revokes the admitted Run. Even a forged direct call must pass the current Server authorization path.

External MCP tools join this same catalog with exact connection-qualified names, provenance and schema fingerprints. External tools that declare they write stay unavailable until approved writes exist; discovery creates no new approval or write authority.

## Outbound MCP connections

The Server brokers read-only Streamable HTTP MCP calls using the MCP client SDK. The reviewed catalog contains Cloudflare documentation (`search_cloudflare_documentation`, `migrate_pages_to_workers_guide`) and DeepWiki public documentation (`read_wiki_structure`, `read_wiki_contents`). Remote `readOnlyHint` annotations never grant authority. Redirects, local stdio, external writes, sampling and interactive OAuth discovery are unsupported. Plans for the rest are in [outbound-mcp-plan.md](outbound-mcp-plan.md).

### Custom URLs

The Server Owner can also connect their own HTTPS MCP server, such as Coolify or DBHub, under **Tools → Discover / Connect → Custom MCP server**. Only the Owner can, only as a Server-owned connection, and a URL cannot change later: a saved credential belongs to one destination. L4 refuses a URL that is not `https://`, contains credentials or a fragment, is an IP address or a special-use name such as `localhost` or `.internal`, or is this Server's own origin. It authenticates with a bearer token, a Cloudflare Access service token or `X-API-Key`.

L4 lists the tools the URL offers and the Owner chooses which ones Agents may use. A tool that declares `readOnlyHint: false` or `destructiveHint: true` is not offered, and neither is a write tool of another L4 Server, because approved external writes do not exist yet. A tool that declares nothing can be chosen, and the form says so. These declarations come from the remote service: the credential is the real limit, so give it read-only access. DBHub declares `execute_sql` read-only only with its `readonly` setting on.

These checks are rules for what may be saved, not a network boundary. On Cloudflare a Worker reaches only public addresses. In Docker, celld has no such limit that we have verified, so a public name that resolves to an internal address would be reached. The Owner already controls that host, and redirects stay disabled.

A person can ask in chat without a Task. The Run's instructions name each shared source and what it holds, and the Agent finds its tools with `search_tools`.

| Rule | Reviewed catalog | Custom URL |
| --- | --- | --- |
| Call after the Run read private data | Blocked | Allowed: the Owner trusts this service with Server data |
| Reading marks the Run private | No | Yes, before the call. `read_url`, `search_web` and catalog connections are then blocked |
| Where the answer appears | Where it was asked | Where it was asked, for everyone in that conversation |

The mark is `agent_runs.private_at`, so deleting a connection does not clear it. It carries to later Runs only while they inherit the transcript: another person in the same conversation, or a changed mandate, starts clean. Agents can send Server data to a custom service in tool arguments, and between two custom services in one Run. Everyone granted a connection reaches everything its one credential reaches. A built-in private source (Tasks, Data, Documents, private repositories, mail) still posts its answer only where the initiator is the only human reader.

A tool that asks for payment through x402 fails with `mcp_payment_required`, is audited as `payment_required` and charges nothing. Remote text from the request does not reach the model.

Both the Agent and initiating person need the explicit **Use external tools** Role grant. Existing Roles and the built-in Admin receive no automatic grant. Owners may manage Server-owned connections, but using one still requires explicit grants to both the Agent (or its Role) and the initiating Member (or their Role). A member-owned connection is private to its owner, including against Server Owner inspection, and may delegate only to selected Agents for Runs initiated by that owner.

Management currently uses signed-in HTTP APIs under `/api/servers/:id/tool-connections`: `GET`/`POST`, `PUT`/`DELETE /:connectionId`, and `POST /:connectionId/refresh`. Agent capabilities and inbound MCP tokens cannot manage connections. Server Settings → Tools provides Installed, Discover / Connect, Permissions, Approvals and Audit views. Create with a reviewed `providerId`, `ownership`, `name`, `grants: {agentIds,memberIds,roleIds}`, and explicit `toolNames`; credentials are optional. Creation is disabled until an explicit refresh validates tool metadata and a subsequent PUT enables it. PUT supplies the full configuration; omitted `credential` preserves it, `null` removes it, and a replacement rotates it. Preserve `credentialExpiresAt` when editing; changing expiry requires replacing credentials. Bearer API keys or manually obtained OAuth access tokens are encrypted with Server/connection-bound authenticated encryption. Automatic OAuth authorization/refresh is not implemented; expiry or authentication rejection requires reconnection. DTOs expose only credential presence and expiry. Restore the Server's original `AUTH_SECRET` with a backup to decrypt its credentials.

At admission, a Run snapshots at most 16 granted connection revisions. `toolConnectionIds` can explicitly select fewer. Tool schemas stay deferred, so a plain question with many visible connections still starts. Child Runs inherit the parent's connection ceiling. New grants never expand a running mandate. Any configuration, refresh or credential change requires a new Run; disabling/deleting a connection or removing either party's Role grant immediately blocks fresh invocations and cached-result replay. Checks repeat after discovery and before returning results, so revocation during network I/O suppresses the result. Each operation owns its MCP client and request IDs; unrelated connections never share sessions. The existing Run tool-call ledger and budgets govern invocation without automatic retry after an uncertain outcome.

The broker limits operations to 15 seconds, RPCs to 10 seconds, network responses to 256 KB, arguments to 16 KB and model-visible results to 64 KB. Oversized results omit structured content explicitly before shortening text into marked excerpts; complete text evidence is preserved when it fits. Credential redaction precedes excerpting, provenance stays intact, and callers must not infer evidence or fields omitted by the limit. Tool schemas are interpreted without dynamic evaluation, capped at 12 KB, depth 12 and 1,000 nodes; remote references and regex schema keywords are rejected. Schema fingerprints include input and output contracts; drift requires explicit refresh and a new Run. The existing eight-selected-tool/32 KB discovery context budget still applies. Responses include connection, remote tool, fingerprint and observation time; remote instructions are untrusted data. Audits store identifiers/status rather than arguments, results, headers or credentials. Secrets remain in the Server HTTP broker and never enter Run DO or Pi metadata.

## Internal AI functions

Server settings → Models → Defaults → AI functions assigns a named connection and model independently for `apps.assist`, `thread.title` and `web.search`. These are bounded Server functions, not Agent Members: they have no Role, tools, computer, schedules or autonomous actions. They do not inherit an Agent/conversation model or the Server default. All start disabled, and unavailable selections never switch to another model. An Exa deployment key remains the explicit search path when configured. After upgrading from automatic OpenRouter search, assign a search model before using that path again.

Apps assistance replaces Jev. Only the initiating Member’s authorized non-archived Database/View names and visible Field names/types enter its catalog; no Record values, Documents, messages, credentials or executable code are supplied. The model returns bounded source indexes and table/list/metric choices. The Server constructs read-only Bindings and checks current authoring resource access on create, edit and publish. Manual App creation and published App execution do not call a model.

Thread title generation sends only an already authorized root message (at most 6,000 characters) and up to 20 filenames, without attachment content or other conversation history. It runs only when a new thread has no explicit name. Generation runs after the deterministic thread is created, so provider latency does not delay conversation creation or Run admission. Before storing a title, the Server checks current access and preserves any intervening rename or root-message deletion. Generated names are stored once; opening or listing a thread does not call inference. Disabled or failed title generation retains the deterministic message-based title; it does not select another provider. Existing thread names are not regenerated.

AI functions also cover media. **Avatars** draws profile pictures with an OpenRouter image model, such as Nano Banana; a Generate button in profile and agent settings shows the picture first, and saving it uses the ordinary avatar upload. **Image descriptions** lets an agent whose model cannot see images receive a vision model's description instead. **Voice transcription** turns voice messages into text for agents. Each function lists only models whose catalog reports the needed capability; descriptions and transcripts reach the agent marked as untrusted data.

Calls retain provider credentials on the Server and enforce a per-Member limit of 20 internal AI requests per minute, a 30-second timeout, no automatic retries and output limits of 2,000 tokens for Apps / 120 for titles. Search keeps its Run mandate and token budget. Personal ChatGPT assignments can serve only their account holder’s requests. Other Members see them as unavailable. The owner Audit includes function configuration and call records without prompts or provider credentials. No schema migration or data backfill is required.

Pi model capabilities and compaction remain separate from these functions. A Run tells Pi its model's own context window and answer limit: what the provider reported when the model was added (OpenRouter's `context_length` and its top provider's answer limit), then Pi's model catalog, then 128,000 and 8,192 tokens for an unknown model. The window is capped at 200,000 tokens, because Pi sends the retained context with every call and the Run's token budget pays for each one; the answer limit is capped at 32,000 tokens and a quarter of the window. Pi compacts through the Run's selected model when the context nears the window, keeping about 20,000 recent tokens verbatim, and also when a provider reports an overflow. The gateway accepts requests up to 4 MB and uses the same answer limit. Images reach the model through the gateway, which resolves them for models that accept them; the conversation's effort setting controls reasoning there. Pi itself is still told that the model takes text only and does not reason.


### Private continuation

A conversation Session coordinates execution; it does not grant its Members access to each other’s private context. Transcript and working-file restoration requires unchanged initiator, Task, exact permission/resource/connection mandate, repository snapshot, model and instructions throughout that Session’s history. Any mixed or changed history starts clean, including when an earlier compatible Run would otherwise be available. Transcript pointers must identify a completed canonical Run archive; there is no arbitrary-key fallback. Within-Run durable recovery remains supported. Existing archives remain private; useful continuation in a mixed conversation requires future explicit context isolation/sharing policy. A clean start does not clear the persistent untrusted-context flag.

### Tools settings and visibility

Server Settings → Tools shows configured providers and connections and offers reviewed read-only MCP sources and, for the Owner, custom URLs. Save disables a connection, Refresh tools validates its contract, and Enable makes it available to eligible new Runs. Invocation requires current Agent and initiating Member grants, the saved connection revision and an execution mode that permits outbound calls. Credentials remain encrypted and are not read back.

Permissions previews the current Agent and initiator intersection without creating a Run. A Task, conversation, Project, Run snapshot or connection revision can narrow it further. Use external tools alone does not share a connection.

Tools Audit exposes only safe identifiers, actor/action/status, tool fingerprints and guarded Run/Task/discussion links. Search is paginated. Server-owned connections are visible to the Owner; personal history is visible only to its owner, including after deletion. Legacy deleted connections with unknown ownership fail closed. General Server/Agent audit views exclude connection events so they cannot bypass these privacy rules. No prompt, arguments, output, arbitrary remote error, credential or secret metadata is returned.

## Exact result publication review (#307, first slice)

Conversation Runs can inspect public and private repositories when both the Agent and the initiating Member have Project and repository access; newly attached or changed environments are excluded from an existing Run. Autonomous conversation Runs answer in the conversation chosen by the initiating Member. After a Run reads a private source (Tasks, Data, Documents, private repositories, delegated results or mail), its full answer is posted there only if that conversation is the initiator's own Direct Message with the Agent; elsewhere the conversation receives a link to the private Run. A role-mode Agent that has read a private source, in this Run or a transcript it inherits, can no longer call arbitrary egress tools (`read_url`, `search_web` and catalog MCP tools), so injected instructions cannot carry private data out. Start a new conversation for unrelated web research. Task-backed Runs retain the private result and sharing review described below.

On a completed private Run, the initiating human with **Approve Agent actions** can select **Review sharing**. The Server stores the exact text (up to 2000 characters), Run/Agent/initiator/Task, original conversation identity, current effective authority and a SHA-256 review digest. The page displays the exact plain text, destination name/ID, audience and 15-minute expiry before a separate **Approve and publish** action. Approval includes everyone with access to that conversation now or later; recipients may copy or forward the text. Email conversations are excluded. There is no destination override, edited-text parameter or Owner bypass into another initiator’s result.

The Server rechecks current Run, Task, repository, Member and Agent authority and the unchanged proposal before claiming a decision, then again inside the conversation actor before message persistence. A single claimed publication uses a dedicated message identity, separate from the automatic safe Run notice. Completed approval requests are idempotent; executing/uncertain outcomes cannot be retried or replaced. Rejected/expired requests remain in the private audit history, with at most five review attempts per Run. A restart cannot turn a recorded decision into another publication. The review state records who decided and when without copying private content into general audit logs.

This review approves only the completed result text. It does not change the Run's execution mode, a box's approvals or other tools. In review mode, pushes and windows have their own review path; in autonomous mode they use the admitted permissions.

## Owner oversight and private Run content (#322)

The Server Owner can inspect Agent audit metadata: initiator, Agent, final status, model, model/tool call counts and tokens used or reserved. These are usage indicators, not a provider billing statement. Ownership or profile administration does not grant another human’s Run prompt, model output, events, transcript or working files. This is the intentional privacy policy for this version. No Owner content-inspection exception is implemented, so there is no unaudited Owner bypass. The audit links only your own Run details; other Runs are marked as private content. Current conversation/Task/repository permissions still govern access to your own artifacts.

Incident investigation uses attributable metadata and voluntary exact-result sharing through the publication review. A future privileged content-inspection workflow would require an explicit product decision, a separate permission and an auditable read-only action. It must never permit steering, continuation, delegation reuse or automatic import of someone else’s private context.

## Historical context and immutable migrations (#321)

Context checks derive trust from the current Session transcript, historical Tasks/tool ledger and source-message author without rewriting Session rows during inspection. Actual tool reads still persist a monotonic untrusted marker before the read begins. Missing Sessions fail closed. Thus historical content remains untrusted even when its stored marker is absent.

Migration 0019 was already merged and includes a one-time backfill. It remains unchanged under the repository rule that merged SQL is immutable. Removing a historical statement requires an explicit schema-history policy change; the forward security check does not depend on that backfill.

## Projects foundation

Projects are Server-local records with versioned names/descriptions and archive state. Projects contain multiple provider-qualified repository references and Tasks. Roles have Read projects / Manage projects and a Projects resource scope, intersected with delegation. Existing roles do not receive project administration implicitly; Owner retains control-plane administration. Managing project metadata never grants Git writes, merge, release, computer execution or provider credentials. Whoever may manage a Project sets its network, secrets and Git flow; merging from L4 needs Approve agent actions in the Project. Email permissions still use the existing per-mailbox read/send/manage policy, described in the Email section of Roles.

A repository reference can identify GitHub, GitLab, Gitea or Cursor by provider origin and path. References alone do not connect credentials or implement provider operations. Executable adapters exist for GitHub and Gitea (including Forgejo). A matching execution configuration of the same provider and origin can be linked to one project reference; its repository identity and base branch must match. Linking/detaching revokes earlier environment snapshots. Project-bound execution checks both current project scope and existing repository/Task/Run authority; archive blocks execution. Ordinary development uses a dedicated branch in the same repository. Forks remain optional.

Task forms expose Project selection; Tasks retain their existing board. Agent execution retains its admitted Project policy ceiling, and later grants cannot expand an existing Run. Project policies and the Delegate project tasks grant support bounded coordination across Agents. Each Project's Git flow sets who merges its pull requests and how (see [Software Factory](software-factory.md#git-flow-and-merge)); release policies are not implemented.

## GitHub connection setup

The Server Owner can create a private GitHub App from Settings → Git → GitHub. **Connect GitHub** opens GitHub directly for a personal account; **Connect a GitHub organization** asks only for the organization name. GitHub creates the App, then continues straight to selecting the repositories it may access, and the connection in L4 lists them. GitHub requires the account's own authorization; an L4 Role never grants account administration. The Server must have a configured HTTPS public origin (HTTP is accepted only for local loopback development). Creation callbacks expire after ten minutes, are bound to the initiating Owner and Server origin, and cannot be replayed. An uncertain exchange is never retried automatically.

The App requests Contents/Pull requests write and Issues/Checks/Statuses/Actions/Deployments/Metadata read. It requests no branch-protection administration or bypass configuration. The selected repositories and existing GitHub branch rules provide an external ceiling; L4 project, Role, repository, Run and tool policies narrow each operation further. GitHub App credentials stay encrypted in this Server database and are never given to an Agent. Backups must retain the matching Server encryption secret separately from the database; restoring a database with another secret cannot decrypt its connections.

After GitHub finishes, refresh connections and choose an explicit connection before discovering repositories or saving an execution configuration. An existing deployment-provided App remains a separate compatibility option; it is never an implicit fallback for a disabled or missing selected connection. **Disable in L4** immediately denies subsequent broker calls using that connection; it does not uninstall or revoke the App on GitHub. Uninstall the App in GitHub when its provider access must also be removed. GitLab and Cursor references do not yet have executable credential adapters.

A Gitea connection stores one bot account's access token, encrypted with the Server secret like a GitHub App key. Only the Owner connects it, from an HTTPS origin; L4 verifies the token against Gitea first. Gitea cannot narrow a token to repositories or operations, so the Server broker does: each client is bound to one repository path and one operation class, and only working-branch writes and pull request create/update are allowed. The bot account's collaborator access is the external ceiling, as selected repositories are for a GitHub App. Gitea repository IDs are numbered per Gitea server, so Role repository scopes name them `gitea:<connection>:<id>` and never collide with GitHub IDs. Compute Nodes never receive the token: a Docker Node fetches source through the Server's read-only `/api/compute-agent/source/<box>.git` with a capability bound to the box and its lease, and pushes an approved commit through a Server-proxied `git-receive-pack` with a capability bound to that approval; Cloudflare compute does both through BoxOutbound. A draft is a `WIP:` title and required checks match commit statuses. A box's push is an ordinary Git push, so commits keep their SHA and executable files are pushed as they are; only `publish_code_changes` without a box still writes through Gitea's contents API.

An enabled Git connection is only one prerequisite for coding. An admitted task-backed Run also needs the current Project and Role permissions, repository access and a connected Compute Node. Propose code changes permits a working branch and draft pull request. An Agent merges only with `factory_merge`, offered where its Project's Git flow is "the Agent after checks"; a person merges from the Task. Release is never an Agent tool.

Compute comes three ways, and the Server speaks one Node protocol to all of them: a Compute Node on the operator's own VPS, Cloudflare Containers in the operator's own account, and L4 Compute, a box per Task started and stopped by llll.gg and paid by the hour of agent work and billed by the minute with no cap on parallel Agents, which is coming. The Server holds no provider key and no provider environment variable; Pi and the model provider remain on the Server. Never quote a price here: the Docs link to [Pricing](https://llll.gg/pricing).
