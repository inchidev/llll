# Governed agents

An Agent is a non-human Member with one assigned Role. Its profile contains its name, instructions and model. Creators with Manage roles can choose or change its Role in the Create/Edit agent dialog. Roles can also be changed in Settings → Roles → Members; Agents appear in that list alongside people. The Owner role cannot be assigned.

## Role permissions

- Using agents: `useAgents` discovers Agents and permits invocation in accessible conversations. It does not reveal other members' private Direct Messages.
- Administration: `manageAgents` edits profiles; it does not by itself permit private conversations or tool execution.
- Approval: `approveAgentActions` approves pending actions in accessible conversations. External email still requires approval.
- Tasks: `readTasks` reads; `writeTasks` creates/updates; `manageTasks` additionally administers boards and destructive operations.
- Data: `readData` reads; `writeData` edits records and Documents; `manageDatabases` additionally changes structure and deletes resources.
- Autonomy: `executeTasks`, `useComputer`, and `manageSchedules` are separate opt-in permissions, never inferred from an administrator role.

Create/Edit agent shows the selected Role's permissions and any missing task-execution or reporting grants. The built-in Member and Admin roles do not allow autonomous task execution. A role manager who holds the necessary grants can explicitly choose **Use task agent role** to create or select a custom role with Read tasks, Create and update tasks, Execute assigned tasks and Send messages. A new role inherits the creator's resource limits and grants no administrative or computer permissions. Save the Agent to apply the selection; existing roles and Agents are never upgraded automatically.

The Role editor selects all or specific Boards, Tables, Documents and Canvases. Selecting no resources permits none of that kind. Grants govern operations; selecting a resource does not grant an operation. Restricted collections cannot create new top-level resources. Role administrators cannot grant permissions or resources they lack.

Internal agent tools check the Agent's own Role plus the initiating person's delegation. Invoking an Agent as Owner never makes the Agent an Owner. MCP independently intersects the current acting Member's role/resource access with connection scopes. Tool access is checked at execution, rather than trusted from model instructions.

## Upgrade behavior

Existing server managers retain Agent use, profile administration and conversational approvals. Existing Task/Data managers retain their previous access. No existing role acquires autonomous execution, computers or schedules through migration. Existing resource access stays unchanged until explicitly restricted.

## Runtime implementation

All profiles use Pi. The default embedded executor uses `@earendil-works/pi-durable` 1.4.0; Docker and Cloudflare Containers use the pinned `@earendil-works/pi-coding-agent` 1.3.0 protocol. Runtime names are internal and there is no runtime selector. The former Think engine is retired; old profile metadata is normalized to Pi, and no Think context is imported. Pi needs Server file storage (KV or R2) and a model provider. Provider keys remain at the Server; compute receives a capability for one active Run.

Runs are durable, bounded attempts. Sessions and archived context belong to one Agent and conversation. Every model/tool request reloads current roles and checks the saved ceiling. Removal, pause, reduced role or resource access revokes execution. Defaults are 15 minutes, 20 model steps/calls, 100 Server tool calls and 64,000 tokens per Run; admission also limits each Agent to two concurrent Runs and each Server to four; admission also limits each Agent to 50 admissions and 250,000 tokens per 24 hours. Queued work shares conversation context sequentially. A tool with an uncertain outcome is never silently replayed.

Web research requires `browseWeb` in both the Agent’s Role and the initiating member’s authority. Search uses `EXA_API_KEY`, or the explicitly assigned `web.search` model on an OpenRouter connection with web search enabled. No first-connection or first-model fallback is used. Public page reading additionally uses configured Browser access. Search returns source URLs and excerpts. Table records and Documents use the same scoped operations as HTTP and MCP. Agents with `writeTasks` can create Tasks; `executeTasks` permits executing assigned Tasks through `execute_task`; child work inherits the original ceiling, has a maximum nesting of two, and consumes the same daily Agent budget. Computer tools additionally require `useComputer` for both the Agent and initiator, and a task-backed Run. Agent results go to review rather than asserting work is accepted.

Schedules support one-time, daily and weekly reminders and task execution. They retain their original role/resource ceiling, preserve the chosen wall time across DST, skip missed repetitions, and deduplicate each occurrence. Current membership and grants are checked before delivery. Changing permissions can block an existing schedule; create a new mandate after reviewing the new role. Manage your schedules at `/schedules`.

### Embedded executor (experimental)

The embedded executor runs `@earendil-works/pi-durable` 1.4.0 inside the Run SQLite Durable Object when neither a Runner nor Cloudflare Containers is configured. It needs the Run DO, file storage and a model provider. Its registered L4 tools use the same Server gateway, current role checks, delegation ceiling, call IDs and result ledger as container execution. Tasks, Data, schedules, web search and configured Browser reads are available only when authorized. There is no local shell or filesystem; do not treat it as a container for arbitrary code execution.

A durable input snapshot and stable submission ID let polling reopen active SQLite work after eviction. Recorded tool results can be read again; uncertain external writes are refused. Stop aborts the harness and in-flight inference, as well as revoking further gateway access. Model output and tool activity stream into bounded Run events and conversation progress. Archives are chunked atomically into bounded SQLite rows; automatic context compaction uses the same inference gateway and budget.

Local celld acceptance on 2026-10-23 used a real OpenRouter model, called `list_tasks` and `search_web`, returned a direct documentation URL, and cancelled an active model call without publishing a result. An independent process test kills execution with SIGKILL after a tool’s external write and resumes from SQLite: the user input and write each occur once. Other tests cover archive ordering, steering at a tool boundary, duplicated steering delivery, permission revocation, inference budgets and multi-megabyte Unicode archive storage. These are local and fixture results; Cloudflare Preview acceptance remains a separate release check.

### Model providers and conversation controls

Server settings → Agents → Model providers stores API keys encrypted with the Server’s `AUTH_SECRET`. Only the Owner can replace credentials, enable a provider, enable OpenRouter web search or choose the Server default. Members with `useAgents` can see available model IDs, never credentials. A blank key preserves the saved key. OpenRouter, Claude and ChatGPT are available through Pi; no alternate agent engine is offered. Legacy bare model IDs retain their deployment endpoint or resolve to one unambiguous enabled connection. Disabled and ambiguous selections fail with an actionable error, never silently falling back to another model. Disabling a saved provider fails closed; importing OpenRouter suppresses the corresponding legacy deployment option. The import action never sends the deployment key to the browser. Existing deployment bindings remain a compatibility fallback until imported.

- OpenRouter: Chat Completions with an API key. Its optional web search plugin is a separately billed, role-gated tool, with at most three sources per search and the Run’s model/token budget.
- Claude: Anthropic API key. Claude Pro/Max subscription authentication is not implemented in embedded Pi. Do not collect Claude.ai credentials or reuse subscription OAuth tokens as shared Server API credentials; see [Claude authentication boundaries](https://code.claude.com/docs/en/legal-and-compliance).

In a one-to-one Agent conversation, the toolbar above the composer selects the provider/model for future Runs, switches Queue/Steer and stops outstanding work. Threads inherit the parent conversation’s model selection. An admitted Run snapshots its model; changing the picker does not switch an in-flight generation. Every root invocation opens a thread in a DM or channel; replies inside that thread keep using it. Queue runs admitted into the same thread share context sequentially. Failed runs post an error with a link to details. Only the initiating Member can retry a stopped Run, under their current permissions. On embedded Pi, Steer adds the initiating member’s new instructions at the next tool boundary of their active Run, using a stable message ID. It cannot inject instructions under another member’s delegation. The interaction follows the [T3 Code composer](https://github.com/pingdotgg/t3code/blob/main/docs/user/composer.md); container adapters currently queue when steering is unavailable. Agent conversations appear in the dedicated Agents app, separately from human Chat.

### VPS executor

Build both images from the checked-out release, then select their immutable digests in `LLLL_AGENT_IMAGE` and `LLLL_AGENT_RUNNER_IMAGE`. Add `self-host/compose.agents.yml` to the Server Compose command, and configure a separate 32+ character `LLLL_RUNNER_TOKEN`, persistent `LLLL_SERVER_ID` and Compose project name `LLLL_PROJECT`. The trusted Runner has Docker control. Agent containers have no Docker socket, public internet route or provider/production credentials; they run as a non-root user with a read-only root, limited CPU/memory/PIDs bounded temporary data (512 MiB), bounded logs and no persistent host file mount. The Server joins their private network solely to provide the authorized gateway. Results/context are archived before compute is removed. Losing an active compute process interrupts the attempt; a new attempt restores archived conversation context and never silently replays uncertain external actions.

### Cloudflare executor

Add the optional `AGENT_COMPUTE` binding for `AgentComputeDurableObject`, a new SQLite class migration, and a Container with `scheduling_policy: "durable_object"` and named `images.pi` pointing at `packages/agent-runtime/Dockerfile` with repository-root build context. The adapter uses the direct Container API, denies public egress and intercepts only the Server gateway. These provider-specific settings stay outside the Pi protocol. Run application builds/deployments only through Workers Builds from Git. The isolated Server Preview supports `LLLL_PREVIEW_PI=1`; it never changes production or customer Servers.

The Docker proof uses the real Pi SDK with a deterministic model fixture; it proves execution/isolation/recovery, not real-model quality. A Cloudflare Preview and authenticated product acceptance are separate required evidence. See [implementation plan](agent-plan.md) for remaining work.

## Untrusted context and sensitive tool calls

The Server enforces a conservative containment policy for #289 before expanding capabilities. Tool results, Task prompts, restored transcripts and messages supplied by another Member are untrusted context. A durable flag belongs to the entire Session: retries, failed reads, cached result replay and fresh Runs in that conversation do not clear it. Migration 0019 backfills existing Sessions with prior Task/tool/transcript context. A new conversation has independent context; it does not acquire authority to disclose another conversation’s data.

Model-selected Server tool writes, publication, schedules and subtask execution require exact human review and are blocked before effects, even on a fresh Run: private human input and profile instructions are not proof of authorization to publish or mutate data. Human actions through the normal interface remain governed by their existing permissions. Model-selected outbound payloads are unavailable until #307 implements exact human review: this includes arbitrary URLs (both path and query), search queries, MCP arguments, repository file paths and GitHub issue/PR selectors. A read-only remote hint or existing Role grant does not authorize sending private data as arguments. There is no Owner exemption or model-selected override. Fixed-source metadata/tree/check reads and the admitted exact-SHA archive remain available under existing authorization; archive/file bootstrap marks context before returning data. Compute still has no public network egress or production credentials.

Connection administration and SDK/SSE health checks remain available to authorized humans. Enabling a connection does not bypass the invocation guard. Discovery hides blocked actions and direct forged calls fail server-side. This intentionally restricts research and Software Factory workflows until the approval gate is implemented; it is not a working approval queue. Existing LLM inference remains an explicitly configured data processor, not a model-selected exfiltration tool.

Run details shows the untrusted-context state and bounded context-policy decisions. These decisions indicate only that the context guard allowed/blocked a call, not that an operation completed. They contain known tool/effect categories and reasons, with no arguments, results, URL contents or credentials. External and unknown tool identities are redacted. Existing execution ledgers still control uncertain outcomes and duplicate writes. General Server audit does not receive private tool payloads. Prompt wording is guidance, not the security boundary; this policy does not claim to solve every form of prompt injection. Run details, events, transcripts and files are private to the initiating human. Queue prompts are redacted for other Members. Governed Run progress never broadcasts model text, including historical stored partials. All model-generated final output is retained privately until exact publication review exists, including a clean first Run; shared chat and Task results receive only a Server-generated notice/link, while the fixed Task Review transition remains governed by its existing mandate. Exact human approval for wider publication remains #307.

## GitHub code work

Settings → Repositories configures a source repository and a separate working fork in the same GitHub network. A task selects that environment; Roles select source repositories by their stable GitHub IDs. Both the initiating Member and Agent require `useComputer`, task access and repository access. The Agent additionally requires `proposeCode` to publish changes. Existing administrator roles do not acquire publication permission.

Configure a **dedicated GitHub App**, separate from login OAuth. Put `GITHUB_AGENT_APP_ID` and its PEM `GITHUB_AGENT_APP_PRIVATE_KEY` in the Server's deployment secrets. Install it only on selected sources and working forks. Grant repository Contents read/write, Pull requests read/write, Issues read, Checks read and Commit statuses read. The broker mints narrower single-repository tokens per operation: source Contents read; fork Contents write; source Pull requests write; source Checks/statuses read. Tokens and the App key never enter compute. Repository discovery uses metadata-only credentials and revokes them after use. All GitHub API requests use manual redirects; credentialed requests never follow a redirect. The archive broker accepts only GitHub’s 302/303 redirect to the configured repository’s exact admitted SHA on codeload.github.com, downloads without App credentials, rejects further redirects and rechecks current access before returning cached or downloaded code.

Task-backed code Runs can discover `read_github_repository`, `read_github_issue` and `read_github_pull_request`. These read only the configured source repository: callers select an issue/PR number and a bounded section/page, never a repository URL or HTTP method. Issue comments, PR patches, review summaries and inline comments are paginated at 20 entries for at most 10 pages, with explicit truncation. PR file/review reads recheck the head and base SHA and reject evidence collected across a changing revision. Remote text and patches are untrusted data, not instructions. Issue/PR tokens add only the necessary read permission to the one source repository; App setup must include Issues read. Cached repository archives also require a fresh dedicated-App capability, so a revoked installation cannot reuse private cached code. Current Run, Role, initiator, Task and repository authorization are checked before requests and before returning results. Linking issue/PR metadata in the Task editor and real-installation acceptance remain separate follow-up work.

An admitted Run freezes the environment version, base branch and exact commit/tree. Changing or disabling the environment revokes active Runs and stored schedule mandates. The runtime downloads a bounded source archive through the Server gateway, creates a local Git base, edits files and can run available local checks. Public network access stays disabled: package downloads and network-dependent tests are unavailable in this first runtime. Dependency-heavy projects must rely on their independent CI checks; agent reports are not CI evidence.

`publish_code_changes` gathers local changed text files and creates or updates one Run-owned branch (`l4-agent/<run-id>`) in the working fork, then a draft PR to the source's configured base. Proposals cannot change `.github` or `.git`, force-push, change the base branch, merge, label a release or deploy production. Repeated publication recovers the same branch/PR after an uncertain response. A branch changed outside the Run requires a new reviewed attempt. Required CI names are checked against the exact published commit; missing or failed checks keep it unverified. Preview links must use HTTPS on configured domains; their presence does not prove authenticated product acceptance.

Computer outputs are bounded to 100 changed files and a 2 MB JSON archive, including binary files and deletions; individual files are at most 500 KB. The Run page downloads the archive through current conversation/task/repository authorization. Future attempts restore files only from the same conversation, task, environment version and base commit. Repository archives are limited to 20 MB compressed / 200 MB expanded and 10,000 ordinary files/directories; links and special files are rejected. A fresh base commit starts with fresh files. Results and transcripts remain in private Server storage after ephemeral compute is removed.

MCP `create_table` requires the explicit `data:manage` connection scope plus the current Role's table administration and resource grants. Existing tokens do not gain this scope. HTTP, internal tools and MCP share the same table/record services and current-role checks.

Production publishing stays with the protected GitHub release process: a human reviews and merges a release PR with the release label and shared version increase. That authority and its credentials are outside the agent runtime and GitHub broker.

## Model connections

The Server owner manages connections in Server settings → Agents → Providers. Agents and Providers have separate searchable, paginated lists. Model defaults appears before the provider list. The owner-only Audit tab separates Run status and usage from agent-related configuration changes and actions; both views support search and pagination, and Run rows omit prompts and transcripts. A row opens Run details with its prompt, events, selected model, individual model requests, safe provider errors, archived transcript download and retry. Access is rechecked against the conversation and any Task/code environment. Multiple connections of the same provider type can have distinct names. API-key connections show only a masked key fragment to the owner. Model catalogs come from the provider; choose models by name instead of entering IDs. The conversation picker combines the connection name and model, and searches a bounded model page on the Server.

ChatGPT / Codex uses **Continue with ChatGPT** with the [official open-source OAuth flow](https://developers.openai.com/siwc/token-sharing-open-source/sign-in). Pi remains the runtime. The owner authorizes ChatGPT plan usage; that connection can pay only for Runs initiated by that same member. It does not sign anyone into L4, link local Accounts, or grant membership. Tokens and refresh credentials are encrypted on the Server and never passed to Pi. Model selection and inference use the public OpenAI API and the account's model catalog. Live ChatGPT authentication/inference has not been accepted yet; OAuth, renewal, identity validation and stream termination have fixture coverage.

For a local HTTP Server, the browser returns to `127.0.0.1` on the Server port. A remote Server offers a downloadable Node 24 sign-in helper: run the displayed command on the computer hosting the browser. The helper listens only on `127.0.0.1:1455`, opens OpenAI sign-in, and relays the one-time callback to the chosen HTTPS Server. It writes no credential file. Removing a ChatGPT connection stops local use and attempts to revoke the renewable session; if remote revocation fails, disconnect L4 in ChatGPT settings.

In an agent DM, a message starts a reply thread. Direct Run admission into the DM root is rejected. New messages queue in send order across that DM's threads; **Steer** on an already queued message submits it to the sender's running embedded Pi attempt at its next tool boundary. If steering is unavailable, the message stays queued. If delivery is uncertain, it is not executed a second time. **Stop** appears while the agent is working and cancels pending work before the active attempt. Separate conversations can run concurrently within the existing limits.

## Model selection and task completion

Connecting a provider adds choices; it never selects the first model as a Server default. Choose the default explicitly in Providers, or select an Agent/conversation model. A disabled default does not fall back to another model. Explicit operator model configuration remains supported; an AI binding by itself does not enable a default. Workers AI appears as a deployment connection whose account access, quota and compatibility are verified on use. Known OpenRouter models without tool support are excluded from Agent choices; missing capability metadata is not proof of incompatibility.

Task execution requires Read tasks and Execute assigned tasks, plus access and Send messages in the report conversation, for both the Agent and initiator. Admission checks these before inference. Completion can record only that Run’s result on its assigned, unchanged Task; it does not grant general task editing. Results move to Review. Human changes, reassignment and archival are preserved.

Assignment alone does not start execution: Ready means available for an explicit start. Choose **Create and run** when creating an Agent-assigned Task, or **Run assigned agent** at the top of a saved Task. A separate report channel is optional: without one, the Agent posts in the Task’s discussion, which uses the board’s existing access rules. The discussion is created on demand when the caller can write Tasks. Save any pending Task edits before starting; paused Agents and archived Tasks explain their blocked action beside the button. Both actions use the same authorization and admission checks. Conversation reports identify the Task number, title and current status, link back to its board and detail, and include the result below.

Computation, Task-result recording and report delivery have independent states on the Run page. Delivery failures retain the computed result. Pending delivery retries are bounded; only the original initiator can explicitly retry blocked delivery, under current permissions and the saved mandate. Retrying delivery does not call the model. Successful delivery is not posted twice.

Every model request includes the current UTC time and Server timezone (UTC by default). The `get_current_time` tool refreshes this reference during longer work. Ambiguous scheduling timezones still require clarification.

## Tool discovery

Both embedded and container Pi start with `search_tools`, `get_tool_details` and the current-time tool. Other Server tool schemas are deferred. Search ranks only the Run's currently permitted capabilities and returns at most eight short summaries without schemas or resource names. Load an exact identity with `get_tool_details(name, purpose)` to expose its schema on the next model request. The purpose is a short public description of the requested work, not private model reasoning; it appears in Run activity. Details include effects, prerequisite action, output/evidence, cost hints and trust boundaries. Search metadata does not grant permission.

Each Run may select at most eight tools, with at most 16 KB per descriptor and 32 KB total. Discovery and selection use the existing tool-call ledger and budget. Unselected schemas do not enter model requests. Missing matches and unavailable details explain that a capability is missing. Search disappears when its assigned provider is disabled or unavailable, unless Exa is explicitly configured; page reading requires Browser access. Repository tools require the existing repository/computer mandate. Connection changes are checked on the next discovery and invocation; reduced Role/resource authority revokes the admitted Run. Even a forged direct call must pass the current Server authorization path.

External MCP tools join this same catalog with exact connection-qualified names, provenance and schema fingerprints. New external mutating tools remain disabled until #307; discovery creates no new approval or write authority.

## Outbound MCP connections

The Server brokers read-only Streamable HTTP MCP calls using the MCP client SDK. The reviewed catalog currently contains Cloudflare documentation (`search_cloudflare_documentation`, `migrate_pages_to_workers_guide`) and DeepWiki public documentation (`read_wiki_structure`, `read_wiki_contents`). Remote `readOnlyHint` annotations never grant authority. Custom URLs, redirects, local stdio, external writes, sampling and interactive OAuth discovery are unsupported. These fixed public HTTPS destinations, Workers' `global_fetch_strictly_public`, exact URL checks and disabled redirects prevent user-selected private destinations and redirect/rebinding pivots; adding a provider requires code review.

Both the Agent and initiating person need the explicit **Use external tools** Role grant. Existing Roles and the built-in Admin receive no automatic grant. Owners may manage Server-owned connections, but using one still requires explicit grants to both the Agent (or its Role) and the initiating Member (or their Role). A member-owned connection is private to its owner, including against Server Owner inspection, and may delegate only to selected Agents for Runs initiated by that owner.

Management currently uses signed-in HTTP APIs under `/api/servers/:id/tool-connections`: `GET`/`POST`, `PUT`/`DELETE /:connectionId`, and `POST /:connectionId/refresh`. Agent capabilities and inbound MCP tokens cannot manage connections. Server Settings → Tools provides Installed, Discover / Connect, Permissions, Approvals and Audit views. Create with a reviewed `providerId`, `ownership`, `name`, `grants: {agentIds,memberIds,roleIds}`, and explicit `toolNames`; credentials are optional. Creation is disabled until an explicit refresh validates tool metadata and a subsequent PUT enables it. PUT supplies the full configuration; omitted `credential` preserves it, `null` removes it, and a replacement rotates it. Preserve `credentialExpiresAt` when editing; changing expiry requires replacing credentials. Bearer API keys or manually obtained OAuth access tokens are encrypted with Server/connection-bound authenticated encryption. Automatic OAuth authorization/refresh is not implemented; expiry or authentication rejection requires reconnection. DTOs expose only credential presence and expiry. Restore the Server's original `AUTH_SECRET` with a backup to decrypt its credentials.

At admission, a Run snapshots at most four granted connection revisions. `toolConnectionIds` can explicitly select fewer; more than four visible connections requires selection. Child Runs inherit the parent's connection ceiling. New grants never expand a running mandate. Any configuration, refresh or credential change requires a new Run; disabling/deleting a connection or removing either party's Role grant immediately blocks fresh invocations and cached-result replay. Checks repeat after discovery and before returning results, so revocation during network I/O suppresses the result. Each operation owns its MCP client and request IDs; unrelated connections never share sessions. The existing Run tool-call ledger and budgets govern invocation without automatic retry after an uncertain outcome.

The broker limits operations to 15 seconds, RPCs to 10 seconds, network responses to 256 KB, arguments to 16 KB and model-visible results to 64 KB. Oversized results omit structured content explicitly before shortening text into marked excerpts; complete text evidence is preserved when it fits. Credential redaction precedes excerpting, provenance stays intact, and callers must not infer evidence or fields omitted by the limit. Tool schemas are interpreted without dynamic evaluation, capped at 12 KB, depth 12 and 1,000 nodes; remote references and regex schema keywords are rejected. Schema fingerprints include input and output contracts; drift requires explicit refresh and a new Run. The existing eight-selected-tool/32 KB discovery context budget still applies. Responses include connection, remote tool, fingerprint and observation time; remote instructions are untrusted data. Audits store identifiers/status rather than arguments, results, headers or credentials. Secrets remain in the Server HTTP broker and never enter Run DO or Pi metadata.

## Internal AI functions

Settings → Agents → Providers → AI functions assigns a named connection and model independently for `apps.assist`, `thread.title` and `web.search`. These are bounded Server functions, not Agent Members: they have no Role, tools, computer, schedules or autonomous actions. They do not inherit an Agent/conversation model or the Server default. All start disabled, and unavailable selections never switch to another model. An Exa deployment key remains the explicit search path when configured. After upgrading from automatic OpenRouter search, assign a search model before using that path again.

Apps assistance replaces Jev. Only the initiating Member’s authorized non-archived Database/View names and visible Field names/types enter its catalog; no Record values, Documents, messages, credentials or executable code are supplied. The model returns bounded source indexes and table/list/metric choices. The Server constructs read-only Bindings and checks current authoring resource access on create, edit and publish. Manual App creation and published App execution do not call a model.

Thread title generation sends only an already authorized root message (at most 6,000 characters) and up to 20 filenames, without attachment content or other conversation history. It runs only when a new thread has no explicit name. Generation runs after the deterministic thread is created, so provider latency does not delay conversation creation or Run admission. Before storing a title, the Server checks current access and preserves any intervening rename or root-message deletion. Generated names are stored once; opening or listing a thread does not call inference. Disabled or failed title generation retains the deterministic message-based title; it does not select another provider. Existing thread names are not regenerated.

Calls retain provider credentials on the Server and enforce a per-Member limit of 20 internal AI requests per minute, a 30-second timeout, no automatic retries and output limits of 2,000 tokens for Apps / 120 for titles. Search keeps its Run mandate and token budget. Personal ChatGPT assignments can serve only their account holder’s requests. Other Members see them as unavailable. The owner Audit includes function configuration and call records without prompts or provider credentials. No schema migration or data backfill is required.

Pi model capabilities and compaction remain separate from these functions: embedded Pi currently accepts text only, uses a conservative 24,000-token context and 4,096-token output limit, and compacts through the Run’s selected model. A provider’s vision/reasoning capabilities do not imply that this gateway implements them.


### Private continuation

A conversation Session coordinates execution; it does not grant its Members access to each other’s private context. Transcript and working-file restoration requires unchanged initiator, Task, exact permission/resource/connection mandate, repository snapshot, model and instructions throughout that Session’s history. Any mixed or changed history starts clean, including when an earlier compatible Run would otherwise be available. Transcript pointers must identify a completed canonical Run archive; there is no arbitrary-key fallback. Within-Run durable recovery remains supported. Existing archives remain private; useful continuation in a mixed conversation requires future explicit context isolation/sharing policy. A clean start does not clear the persistent untrusted-context flag.

### Tools settings and visibility

Server Settings → Tools is available to Roles that use/manage Agents or use external tools. Installed shows configured capability providers and connections you manage; Discover / Connect offers only reviewed read-only MCP sources. Save disables a connection, Refresh tools validates the contract, and Enable prepares its reviewed contract for new Runs; invocation still requires the sensitive-action review gate. Edit the reviewed tool selection and Agent/Member/Role grants to restrict a connection. Disabling or revoking it immediately stops subsequent calls in active Runs. Personal connections remain private to their owner. Credentials are password inputs, never read back, and cleared after submission or closing the editor.

Permissions previews the current intersection for an Agent with you as initiator; it creates no Run or executable capability. Task, conversation, runtime-only requirements and a Run snapshot may narrow exposure further. The Role editor exposes Use external tools under Integrations; it does not share a connection by itself. Exact-action approvals are unavailable until #307. Model-selected outbound calls and writes after untrusted context remain blocked; the UI explains this restriction.

Tools Audit exposes only safe identifiers, actor/action/status, tool fingerprints and guarded Run/Task/discussion links. Search is paginated. Server-owned connections are visible to the Owner; personal history is visible only to its owner, including after deletion. Legacy deleted connections with unknown ownership fail closed. General Server/Agent audit views exclude connection events so they cannot bypass these privacy rules. No prompt, arguments, output, arbitrary remote error, credential or secret metadata is returned.
