# Deploy a standalone Server

Deploy one Server, claim its owner, then invite members. Accounts, files and conversations belong to this Server. It works at its direct origin and through the optional Shell.

## Cloudflare

The Shell logo opens **My servers** at `/servers` on the current origin, including in Previews. This device-local list opens saved Server connections and can remove their bookmarks; removing a bookmark does not delete the Server or its Account. When a saved Server stops answering, the official site checks its address on the Shell's behalf; only Cloudflare's answer that no Worker serves that `workers.dev` address (error 1042) counts as deleted. The Shell then forgets the Server on this device and says so. Outages, timeouts and custom domains are never forgotten automatically. **Remove from this device** stays available on the slow-loading screen and in `/create`. The logo is highlighted on this page. Each Server continues to own its login and membership.

The Shell's plus button opens `/create`, with three tabs: **Connect**, **Cloudflare** and **VPS**, and is highlighted while that page is open. Connecting by address, configuring a Cloudflare deployment and reading VPS setup all stay on that page. Tab links use `?tab=cloudflare` or `?tab=vps`. Existing `/open` and `/deploy` links redirect to `/create` while preserving connection parameters; old `/deploy?method=vps` links select VPS. Legacy `/servers?server=…` connection links also continue to open `/create`.

The Cloudflare tab selects an account, Server name, admin email and published standalone release, then installs that release through the customer's own Cloudflare OAuth grant. A new Server starts on the customer's `workers.dev` hostname; domain selection is not part of this installer. The PWA starts at `/create`; its existing manifest ID remains stable for already installed copies.

The owner setup claim stays in that tab's session storage across reloads and is removed after owner creation. If the tab was closed or the installer session expired, reconnect Cloudflare in `/create`, refresh Your Servers, and choose **Finish setup on your Server** or **Recover setup link**. Recovery verifies the authorized account and Worker, then replaces the pending claim only if the Server has no Owner or login Accounts. It never resets an existing Owner. The private link stays in the encrypted installer session; saved Shell bookmarks contain no claim.

After installation, the owner can add Cloudflare custom domains in the Server under **Server settings → Deployment → Domain**. A hostname must be in an active zone in the same Cloudflare account. Adding one attaches it as a Worker custom domain, keeps `workers.dev` enabled and leaves every existing address working. One address is the primary; the others are aliases. Login, sessions, Shell embedding, links, uploads, backups, MCP and realtime accept the primary and every alias, while the Server's UUID stays the identity. New links, Shell bookmarks and background email use the primary. **Make primary** promotes an attached alias without removing the old primary. **Remove** detaches an alias; the primary cannot be removed until another address is primary. When the Server keeps Cloudflare access (see [updates](server-updates.md#update-from-the-server)), it makes the change itself, and Mail and Live connect with the same access instead of a separate token. Otherwise the official site performs the Cloudflare change through the owner's one-time OAuth grant; the Server receives only a single-use request capability, never an account-wide credential. Only configured addresses are trusted: a hostname that merely reaches the Worker is rejected for sessions and mutations and is never added automatically. If the Server uses an external identity provider, allow its callback URL on each address you enable there.

No Git integration, GitHub connection or Workers Builds deployment token is required. The customer approves Workers, D1, KV, R2 and domain permissions through Cloudflare OAuth; authorizations created by an older release may need fresh consent through **Reconnect Cloudflare**. Before allocating any resource, the installer downloads the selected published release and verifies its `SHA256SUMS`, the bundle hash and every module hash. A missing or mismatched checksum aborts without creating a Server. The installer uploads only that published, immutable artifact and never unreleased or locally built code.

The installer provisions the Server's D1 database, TICKETS KV, Durable Object namespaces and Worker. When R2 is enabled it also provisions private FILES storage and a separate BACKUPS bucket. If R2 is unavailable, a release with `basic-kv-storage-v1` uses file storage in the existing TICKETS namespace. It then verifies the Server's public discovery response before completing. Every step is resumable; a retry keeps the same resource names and the private owner claim. See [Server updates](server-updates.md) for release selection, verified backups and recovery.

**One UUID names everything.** The installer generates a UUIDv4 and uses it for the Worker (`llll-<uuid>`), the D1 database (`llll-<uuid>-db`), the private files bucket (`llll-<uuid>-files`), the backups bucket (`llll-<uuid>-backups`) and the tickets KV (`llll-<uuid>-tickets`). The same value is seeded into the Server's `server_identity.id` before the Worker handles a request, so discovery, backups and membership always agree on identity. A VPS install generates the same UUID into `.env` as `SERVER_ID`.

**Worker env stays minimal and unprefixed.** After install the Worker keeps only `PUBLIC_ORIGIN`, `AUTH_SECRET`, `AUTH_MODE` (with Cloudflare Access bindings when used), `ACCOUNT_ID` and its resource bindings. Owner setup lives in D1: the installer seeds a single pending claim (`server_setup`, token stored only as a digest) and the row is deleted when the owner claims the Server, so `ADMIN_EMAIL`/`SETUP_TOKEN` never exist as Worker bindings on a fresh install. The Server name (chosen during setup), the registration mode and mail settings live in D1 too; changing the Server name in Settings never touches Cloudflare resources.

Updating an existing Server migrates it to this shape: the first upload boots the new Worker, which copies legacy settings (`APP_NAME`, `AUTH_REGISTRATION_MODE`, `LLLL_EMAIL_DOMAINS`, `MAIL_APP_HOSTNAME`, `MAIL_DEFAULT_LOCAL_PART`, the setup bindings and `LLLL_ACCOUNT_ID`/`LLLL_WORKER_NAME`/`LLLL_VERSION`/`LLLL_SERVER_MARKER`/`BACKUP_BUCKET_NAME` and zone metadata) into D1, and a second metadata upload then removes those bindings. The stored UUID, accounts and files are unchanged; where a Worker name does not follow `llll-<uuid>`, the Server stores its real Worker name in D1 and keeps using it.

After verification, **Finish setup on your Server** opens `/setup#claim=…` in a new tab on the Server's own origin, so the browser can generate and save its password for that domain. The installer stays open, observes readiness and saves a Shell bookmark; it does not navigate the owner into an iframe for setup. Its admin email is fixed by the installer; the owner chooses a password on that Server and is signed in immediately. A private, single-use bootstrap credential travels in URL fragments from the installer to the Server’s `/setup`; users do not copy or enter it. It never enters request query strings, public logs or Git. Knowledge of the admin email alone cannot claim the Server. The website retains the encrypted browser-bound OAuth grant within its one-hour installer session so the operator can list L4 Servers in an authorized account and create another Server. Only an explicit OAuth connection renews that session; polling and deployment progress do not extend it. Expired sessions require reconnection. With **Keep Cloudflare access on this Server** (on by default), the installer hands its grant to the Server after it runs, through a single-use capability in the Server's D1, and then forgets it; see [updates](server-updates.md#update-from-the-server).

The Cloudflare tab lists Workers carrying the current L4 Server marker. Server status comes from each Server's public discovery response; "Finish setup on your Server" appears only while that Server is unclaimed and this browser session holds its private claim. Device-local saved addresses remain available after expiry and are labelled separately from a refreshed Cloudflare account inventory. A saved address that the connected account no longer lists is dropped after a successful refresh, and any address the account does not list can be removed from the device. These bookmarks contain no claims or Cloudflare credentials and grant no Server membership. Creating another Server retains earlier setup claims only inside the same encrypted installer session. Access-token expiry, installer-session expiry and each Server's own login session are independent.

The official `llll` Worker also runs the Telegram Shell's notifications relay. Its bot username is the `TELEGRAM_BOT_USERNAME` variable and its token the `TELEGRAM_BOT_TOKEN` secret; without the token the relay answers 503 and Servers keep only Web Push. `/api/telegram/subscribe` checks signed Mini App launch data (up to an hour old) and returns a deterministic AES-GCM token sealing the Telegram chat and Server UUID with a key derived from `AUTH_SECRET`; rotating `AUTH_SECRET` invalidates every Telegram subscription. `/api/telegram/notify` is called by Servers without a browser Origin, is rate limited per token, and sends a fixed, content-free message. The relay stores no subscriptions. A Server only posts a token to an origin in its `EMBED_ORIGINS`.

Our own application deployments — the official `llll` Worker, llll.gg, Landing/Shell/Docs and Previews — may only deploy in Workers Builds from Git. Local Wrangler is limited to types, dry runs and isolated development. Connected Cloudflare API tools administer resources, domains and build configuration; they never upload our application code from the developer machine. Customer Server installation and updates are the exception: they upload only a published, immutable, checksum-verified release artifact through the customer's own OAuth grant.

## VPS / celld

`self-host/docker-compose.yml` is the common celld/RustFS/Caddy stack. It runs an already loaded portable image; `compose.build.yml` adds a local source build and `compose.dev.yml` adds source watching and Client HMR. See [self-host setup](../self-host/README.md) and [local development](local-development.md). The release-pinned [VPS installer](vps-installer.md) adds public HTTPS, repeatable setup and backup/restore/upgrade commands through `compose.vps.yml`. It becomes available only when a release containing it is published. The [Coolify template](../self-host/coolify/README.md) uses the published `ghcr.io/inchidev/llll` image and Coolify's own proxy; its updates are an image tag.

Configure `PUBLIC_ORIGIN`, `AUTH_SECRET`, `ADMIN_EMAIL`, private `SETUP_TOKEN` and persistent storage credentials in ignored/private operator configuration. Configure public TLS before inviting users; the local launcher defaults to loopback HTTP. Open `/setup`, enter `SETUP_TOKEN`, set the owner password and invite another person.

Optional Software Factory on a VPS needs Docker, a loop device and 17 GiB free disk. `llll factory enable --trust-shared-kernel` installs a root systemd service when `/run/systemd/system` exists. A container or other host whose process 1 is not systemd can prepare the same verified files with `--no-systemd` and start the released `node` by hand; `status` and `logs` say so instead of pretending a journal exists. The published workspace image is accepted when the loaded image id matches the release's image id, config digest or index digest, so both the classic Docker image store and containerd verify it. `LLLL_NO_TLS=true` with `LLLL_DOMAIN=127.0.0.1` publishes the gateway on 127.0.0.1. A Factory failure during a fresh install is reported and leaves the Server installed.

`PUBLIC_ORIGIN` is the primary public origin. On VPS installations, add or remove additional hostnames with `sudo llll domain`; the command updates the Worker's `LLLL_ORIGINS`, the Caddy site addresses and every address's certificate, and verifies discovery on each one before keeping the change. `LLLL_ORIGINS` is a comma-separated fallback for operators who do not use the installer; it must contain only origins this Server should trust.

`PUBLIC_ORIGIN` is the only origin a Server ever stores as its primary address; the Host of an incoming request is never persisted. Without it (unconfigured local development) the Server only trusts the address each request reached.

**Browser security.** HTML responses carry a Content-Security-Policy whose `script-src` allows only same-origin bundles, Turnstile and per-document SHA-256 hashes of the Server's own inline scripts (no `'unsafe-inline'`); zone features that inject or rewrite inline scripts, such as Rocket Loader, are incompatible. Every document, including the shell the PWA caches, comes from the Worker, so it carries the Server's own `frame-ancestors`; the build publishes no static HTML, because static assets bypass the Worker. HTTPS responses send `Strict-Transport-Security: max-age=31536000` without `includeSubDomains`, since operator origins may share a parent domain with unrelated sites. Unsafe requests (`POST`/`PUT`/`PATCH`/`DELETE`) that carry cookies must come from one of the Server's origins (`Origin`, or `Sec-Fetch-Site: same-origin` when no `Origin` is sent); scripts that use a session cookie must send a matching `Origin`. Bearer-token, signed-webhook, compute-node and agent-runtime requests need no browser headers. `GET /api/setup/health` is read-only; anonymous callers receive status, version and branding (plus setup diagnostics before the owner claims the Server), and signed-in members also receive runtime details.

Keep each Server's D1, files and DO state separate. Preserve its original encryption secret and storage across restarts and updates. Operator Docker/SSH credentials do not enter the Client. Verify transport and browser behavior on celld separately from Cloudflare.

## Providers and recovery

RealtimeKit, AI and mail are optional Server-local settings. Cloudflare deployment does not imply they are configured. RealtimeKit's API token remains backend-only; clients receive participant credentials. See [runtime architecture](architecture.md) and [celld reference](self-host/celld.md).

Back up Server D1, live files and encryption/deployment secrets to a destination separate from live files. Backup buckets survive Server deletion. Restore into isolated resources and verify the same UUID, accounts, roles, messages and files. Save local account recovery keys privately; they are single-use and revoke sessions when redeemed.

The active Server schema is `server-v2`, beginning at `drizzle/server-migrations/0000_server_baseline.sql`. Create a fresh database; earlier schemas cannot be upgraded into this line. Published artifacts and Git history remain unchanged.

Published release discovery uses GitHub REST with an optional public-repository token, and falls back to the public release feed on quota responses. Feed entries must name a supported version and expose the deployment artifact and manifest in published checksums; the manifest must declare the matching standalone capability. Installing still verifies every artifact checksum.

## Basic file storage and R2

Without R2, immutable private file payloads use a `files/` prefix in the existing TICKETS KV namespace. A D1 index owns metadata and atomically reserves quota; access still goes through the Server's normal file authorization. The application limit is 20 MiB per file and 500 MiB total. KV's account limits and daily quotas still apply, shared with connection tickets. A temporarily invisible KV value returns a retryable error. This storage does not add a new database or claim unlimited Cloudflare capacity.

**Settings → Storage → Connect R2** uses a fresh browser-bound Cloudflare grant to attach the bucket. Attaching it does not switch existing files. **Move files to R2** explicitly copies and verifies payload hashes in resumable batches. Uploads pause during the copy; reads continue from KV. Only a fully verified copy with no admitted uploads switches the backend. Original KV payloads remain preserved. Backup archives include indexed KV file payloads as well as R2 payloads; connection tickets are excluded. Generic live S3 adapters remain separate work.

### Recovering a browser installation

Reconnect Cloudflare is available even while a grant appears connected. Account email-verification and authorization failures require a new connection; reconnecting retains the installation’s Server UUID, Worker name and owner claim. Progress records show provisioning steps, including R2 or Basic KV file storage. Without a separate backup bucket, backups download to the operator’s device.

Pause and start another retains an unfinished installation in the encrypted, bounded installer session. Resume setup reuses its UUID and existing resources. Pausing and disconnecting do not delete infrastructure. Paused entries expire with the installer session; unwanted resources can be removed separately in Cloudflare. Backup buckets must be retained separately from live resources. Reconnect, pause and resume are blocked while an installation step holds its lease.
