# Self-host walkthrough findings

Historical evidence from the archived prototype, retained as a reproduction guide. These results are not acceptance of the new alpha release.

Record of what a local celld installation walkthrough actually proved, what it disproved, and what remains open. Written after exercising the generated Compose stack end to end. Claims here rest on the running celld runtime and on a real browser, not on the Miniflare fixture.

## How this was verified

The stack was generated by `scripts/self-host-installation.mjs`, run through `docker compose` on colima, and driven over real HTTP. The browser paths were exercised in headless Chrome over the DevTools protocol, because the desktop browser tool was disconnected and server-rendered markup alone cannot show a click that does nothing.

`scripts/test-instance.mjs` was not used for any transport claim below. That fixture builds three Workers and dispatches requests in-process, which bypasses the HTTP layer where two of these findings live. This is the general lesson: a green fixture is not evidence about a WebSocket handshake, a redirect, or a static asset lookup.

## Findings

### 1. Realtime does not complete through the installation proxy on celld

A WebSocket upgrade straight to the celld server returns a correct handshake:

```
HTTP/1.1 101 Switching Protocols
connection: upgrade
upgrade: websocket
sec-websocket-accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

The same upgrade through the installation at `/s/<id>/ws/...` returns `101` with `date` only — none of the three required headers.

The installation does not cause this. `proxyServer` in `apps/instance/src/index.ts` returns the upgrade response unchanged (`if (response.status === 101) return response`), so nothing in our code re-wraps it. The loss happens on the outbound upgrade `fetch()`: celld declares no service bindings, so the installation always takes the `fetch(forwarded)` fallback to the sibling node rather than the `SERVER_<id>` binding used on Cloudflare.

The client is affected because `serverBase()` resolves every server path to `${origin}/s/${serverId}`, and `useWorkspaceSocket`/`useChannelSocket` open `/ws/...` on that base. RFC 6455 requires a client to verify `Sec-WebSocket-Accept`, so the browser handshake fails.

The fixture missed this by construction: `mf.dispatchFetch` hands back a live `webSocket` object in-process, so no handshake headers are ever serialised or checked.

### 2. A selected server is dropped on the next boot, and “Open server” looks like a no-op

`app/composables/useClientServers.ts` returns `native: true` as a literal, and the shipped client bundle runs with `clientMode: "web"`. Two separate consequences follow.

`app/middleware/00-native-server.global.ts` gates on `native`, so every browser is treated as a native shell: any route outside `/connections`, `/deploy`, `/servers` and `/consent` redirects to `/connections` whenever no server is selected at that instant.

`app/plugins/session.ts` gates on `native && !serverOrigin`, so the session is never refreshed while no server is selected.

Measured behaviour of the button: `open()` calls `select()`, which persists the choice correctly, then `location.assign('/')`. On the new document the persisted choice is gone, `discover()` re-creates the directory entry with `servers: []`, and the global middleware returns the browser to `/connections`. The user sees the same screen and concludes the button is broken. The exact line that clears the restored selection was not isolated before the walkthrough stopped; the `clientMode === 'web'` branch in `app/plugins/00-client-router.client.ts` is the outstanding suspect.

### 3. celld serves no single-page-application fallback

`/connections` answers `307` to `/connections/`, and `/connections/` answers `404 Not Found` — although `.output/public/connections/index.html` is present in the image. A path that is not a directory, such as `/channels/general`, is served `index.html` normally. Cloudflare handles both correctly through `not_found_handling: single-page-application`.

The effect is specific to celld self-hosting: reloading or deep-linking any client route whose name is also an asset directory fails. In-session navigation is unaffected because the router never asks the server.

### 4. The creation path itself is sound

Claiming the installation from `owner-claim.txt` produced the owner account. Registering the generated server from `servers.json` returned `status: ready` at version `0.4.6`. `GET /s/main/api/me` returned the owner, the default workspace came up as `main` with `#general` and `#random`, and a message written to `#general` read back correctly. Roles were `owner`, `admin` and `member`; boards, documents, canvases and invites were empty; mail reported `configured: false`, which is expected without a provider; `management.available` was `false`, which is correct because Cloudflare provisioning is Cloudflare-only.

### 5. Environment constraints worth remembering

A prebuilt image must copy the whole `apps/instance` directory, not just `.bundle`, or the worker crash-loops with `Error: no migrations directory`. celld 0.6.2 has no secrets store, so `celld deploy` writes `vars` in plaintext and any short-lived credential must be a one-time code exchanged server-side rather than a signed value. Migrations are applied out of band on celld, so anything schema-shaped must ship as a migration. The generator pins `AUTH_REGISTRATION_MODE=invite_only`, so “a visitor creates their own account” only holds where `REGISTRATION_MODE` can be `open`.

## What this means for the product

The read-only demo should run on Cloudflare as a server inside `sandbox.llll.gg`. That choice avoids findings 1 and 3 entirely: Cloudflare keeps the WebSocket handshake through service bindings and implements the SPA fallback, and it is the only place where open registration is available. A read-only role expressed as bitmask 0 is still not sufficient on its own, because `directMessagePermissions` returns `MemberPermissions & ~startLive`, so DM needs an explicit block rather than the absence of a flag.

A standalone server — `kind: 'server'`, its own origin, no installation — is a different topology from what this walkthrough exercised. It skips the installation proxy and therefore both of the routing findings above. It is also what was actually wanted when this stack was stood up; the installation was raised because it is the multi-server entry point, not because the task required it.

The shell hero still shows a login form rather than live product, because `connect()` never signs anyone in. That gap is independent of everything above.

## Open items

Isolate the line that clears the restored selection, then make `native` reflect the real runtime instead of a constant, and re-check `/` boot with a selected server.

Decide the local development story: a standalone server, an installation stack, or both, before more work assumes the installation proxy.

Reduce finding 1 to a minimal celld reproduction — a Worker upgrading an outbound `fetch()` to a sibling node and returning the response — before reporting it upstream.

Keep transport-level verification on the target runtime. Where a fixture cannot model the handshake, the redirect or the asset lookup, the fixture does not get to close the question.
